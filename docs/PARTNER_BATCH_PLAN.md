# План Улучшений (Партиями) для Финального Решения

Документ для партнера.  
Цель: привести решение к уровню `10/10` по качеству реализации и соревновательной устойчивости, сохранив полное соответствие ТЗ и поддержку двух датасетов.

## Общие целевые критерии

1. Полное соответствие ТЗ:
- запуск одной командой `python run.py`;
- чтение только из `data/`, запись только в `output/`;
- максимум 5 сгенерированных признаков;
- стабильная работа в лимите 600 секунд;
- воспроизводимость.

2. Соревновательное качество:
- сильные и устойчивые признаки, без утечек таргета;
- стабильный отбор лучшего набора на CV;
- переносимость между разными структурами датасетов.

3. Универсальность:
- поддержка датасета #1 (депозит);
- поддержка датасета #2 (повторная покупка товара);
- единый пайплайн выбора стратегии.

---

## Партия 1 — Compliance Hardening (ТЗ без компромиссов)

### Что делаем
1. Дожимаем обязательные проверки:
- строгая проверка непустых ключей в `.env` для выбранного LLM-провайдера;
- жесткая валидация входных/выходных файлов и лимита фич (`<=5`);
- логическая защита от утечек (`target` никогда не попадает в генерацию признаков).
2. Дожимаем воспроизводимость:
- фиксируем seed везде, где есть случайность;
- стабилизируем порядок обхода таблиц/колонок.
3. Дожимаем runtime-контроль:
- тайм-бюджет по этапам;
- graceful fallback при нехватке времени.

### Критерий готовности
- `uv run python run.py` стабильно успешен;
- `uv run python src/utils/check_submission.py` стабильно успешен;
- runtime стабильно с запасом (`< 300 сек` локально).

---

## Партия 2 — Универсальный Слой Понимания Схемы

### Что делаем
1. Вводим `dataset profile`:
- определяем тип набора (deposit vs repeat-purchase) по ключевым полям;
- извлекаем сущности и ключи (`id`, `user`, `product`, `order`, `target`).
2. Добавляем `schema graph`:
- граф связей таблиц по ключам;
- приоритетные пути join для генераторов.
3. Подключаем `readme/data_dictionary parser`:
- извлекаем подсказки по ролям колонок и типам;
- используем подсказки в join-planner и LLM prompt.

### Критерий готовности
- корректная авто-идентификация обоих датасетов;
- детерминированное построение join-плана.

---

## Партия 3 — Feature Factory для Датасета #1 (Deposit)

### Что делаем
1. Усиливаем кандидаты для `client_data`:
- агрегаты по числовым полям (robust stats);
- частотные/редкостные кодировки категорий;
- взаимодействия числовых признаков (ratio/diff/log).
2. Усиливаем join-aware признаки:
- стабильные агрегаты из связанных таблиц;
- readme-aware weighting ключей.
3. Вводим candidate diversity:
- не дублировать эквивалентные наборы;
- штраф за высокую корреляцию между фичами.

### Критерий готовности
- минимум 6–10 качественных кандидатных наборов;
- прирост против текущего baseline по CV.

---

## Партия 4 — Feature Factory для Датасета #2 (Repeat Purchase)

### Что делаем
1. Специализированные блоки признаков:
- `user`-фичи: активность, интервалы, размер корзины;
- `product`-фичи: популярность, reorder-rate, категориальные агрегаты;
- `user_product`-фичи: частота, давность, повторяемость пары;
- `order`-time признаки: сезонность/час/день недели.
2. Ключевые join-цепочки:
- `train/test` + `users` по `user_id`;
- `orders` + `order_items` по `order_id`;
- сведение к `(user_id, product_id)` и затем в `row_id`.
3. Контроль утечек:
- никакого использования `target` в фичеинжиниринге;
- time-aware признаки строим только из истории `prior/train` согласно структуре.

### Критерий готовности
- генератор для датасета #2 стабильно создает валидные фичи;
- одинаковая структура признаков в `output/train.csv` и `output/test.csv`.

---

## Партия 5 — Search/Selection Engine (Выбор лучших 5 фич)

### Что делаем
1. Переходим от “один набор → одна оценка” к поиску:
- пул кандидатов;
- greedy forward selection до 5 фич с проверкой добавленной ценности.
2. Стратегия CV:
- stratified CV для общих случаев;
- group-aware CV (например по `user_id`) для набора #2, где это критично.
3. Функция выбора:
- maximize CV AUC;
- penalize нестабильные/избыточно коррелирующие признаки.

### Критерий готовности
- выбранные 5 фич устойчиво лучшие на повторных прогонах;
- variance CV ниже текущего уровня.

---

## Партия 6 — LLM как Умный Proposer, не как Executor

### Что делаем
1. LLM только предлагает идеи в строгом DSL (уже есть база, расширяем):
- ограниченный набор операций;
- schema-aware prompt + краткая статистика по колонкам.
2. Multi-attempt/self-consistency:
- 2–3 предложения плана;
- структурная валидация;
- выбор лучшего по proxy-сигналу до CatBoost CV.
3. Кэширование и бюджет токенов:
- повторно не дергать LLM при одинаковом профиле схемы;
- лимит токенов на запуск.

### Критерий готовности
- LLM-кандидаты регулярно участвуют в финальном шортлисте;
- стоимость и время LLM под контролем.

---

## Партия 7 — Эксперименты, Абляции, Анти-Оверфит

### Что делаем
1. Вводим протокол экспериментов:
- лог: датасет, кандидат, CV mean/std, время, победитель;
- фиксированные конфиги.
2. Абляции:
- выключаем по одному блоку генераторов;
- проверяем вклад каждого.
3. Стресс-тест:
- прогон на двух датасетах подряд;
- проверка устойчивости к отсутствию части вспомогательных таблиц.

### Критерий готовности
- есть таблица экспериментов с подтвержденным выбором архитектуры;
- нет регрессий по runtime и формату.

---

## Партия 8 — Release & Submit Strategy

### Что делаем
1. Финальная упаковка:
- `presubmit` чек + архив;
- проверка состава zip (без мусора, но с `.env`).
2. Две попытки сабмита (по регламенту):
- Attempt 1: лучший стабильный вариант;
- Attempt 2: улучшенный вариант только при подтвержденном локальном приросте.
3. Freeze-политика:
- никаких рискованных правок в день сабмита без прогона всех чеков.

### Критерий готовности
- архив собирается одной командой;
- оба датасета проходят локальные проверки;
- есть явный decision log, почему выбран финальный вариант.

## Definition of Done (финальная)

1. Полный успех `run.py` и `check_submission.py`.
2. Стабильный runtime сильно ниже 600 сек.
3. Поддержка обоих датасетов без ручного редактирования кода.
4. Максимум 5 признаков, одинаковая структура train/test.
5. Повторяемые результаты при одинаковом seed.
